DOTAZ 3: [Wildcard] Vyhledání všech stanic v aglomeraci Ostrava podle masky
################################################################################

1. Zadání v přirozeném jazyce:
Vyhledejte všechny stanice, jejichž název stanice obsahuje slovo "Ostrava"
v libovolné pozici názvu, nebo jejich kód začíná předponou "OST-".

2. Přesný příkaz (Kibana Dev Tools / REST API):
POST /stanice/_search
{
  "query": {
    "bool": {
      "should": [
        {
          "wildcard": {
            "station_name.keyword": {
              "value": "*Ostrava*",
              "case_insensitive": true
            }
          }
        },
        {
          "prefix": {
            "station_id": "OST-"
          }
        }
      ],
      "minimum_should_match": 1
    }
  },
  "_source": ["station_id", "station_name", "district", "station_type", "elevation"]
}

  dosahuje hodnoty 1.68 (velmi dobrá až dobrá kvalita).

DOTAZ 6: [ES|QL vs Query DSL] Srovnávací analýza znečištění podle typu stanice
################################################################################

1. Zadání v přirozeném jazyce:
Z obou let měření kvality ovzduší (`kvalita_ovzdusi*`) vyberte pouze záznamy
se zhoršenou až velmi špatnou kvalitou ovzduší (index AQI >= 4). Seskupte je
podle typu stanice a spočítejte pro každý typ stanice:
- celkový počet takových měření,
- průměrnou koncentraci PM10,
- průměrnou koncentraci PM2.5,
- průměrnou koncentraci NO2.
Výsledky seřaďte sestupně podle průměrné koncentrace PM10.

--------------------------------------------------------------------------------
A) Varianta v novém dotazovacím jazyce ES|QL (Elasticsearch Query Language):
--------------------------------------------------------------------------------
POST /_query
{
  "query": """
    FROM kvalita_ovzdusi*
    | WHERE aqi_index >= 4
    | STATS pocet_mereni = COUNT(),
            prumer_pm10 = AVG(pm10),
            prumer_pm25 = AVG(pm2_5),
            prumer_no2 = AVG(no2)
      BY station_type
    | SORT prumer_pm10 DESC
  """
}

Ukázka výstupu ES|QL:
{
  "columns": [

C) Podrobné porovnání ES|QL vs. Query DSL:
--------------------------------------------------------------------------------

1. Syntaxe a čitelnost:
   - ES|QL používá lineární sekvenční pipeline oddělenou znakem svislítka `|`
     (obdoba UNIX pipe nebo SQL dotazu), což odpovídá přirozenému myšlenkovému toku:
     vezmi index -> zfiltruj -> spočítej statistiky -> seřaď. Dotaz má pouze 7 řádků.
   - Query DSL vyžaduje hluboce zanořený stromový JSON formát s klíči `query`,
     `bool`, `filter`, `range`, `aggs`, `terms` a vnořenými sub-agregacemi.
     Dotaz má 38 řádků a je náchylnější k syntaktickým chybám v závorkách.

2. Formát výstupních dat:
   - ES|QL vrací kompaktní tabulkovou strukturu (`columns` a `values`), která je
     okamžitě připravena pro vykreslení do tabulky nebo převod do Pandas DataFrame.
   - Query DSL vrací hluboce vnořenou stromovou strukturu (`aggregations ->
     podle_typu_stanice -> buckets -> prumer_pm10 -> value`), kterou musí klientská
     aplikace manuálně procházet a parsovat.

3. Řazení podle agregované metriky:
   - V ES|QL stačí jednoduše přidat klauzuli `| SORT prumer_pm10 DESC`.
   - V Query DSL je nutné uvnitř klauzule `terms` explicitně definovat objekt
     `order: { "prumer_pm10": "desc" }`, který odkazuje na název vnořené sub-agregace.

4. Kdy se co hodí:
   - ES|QL je čitelnější a rychlejší na napsání pro jednoduché analytické dotazy
     typu "seskup, spočítej, seřaď" - syntaxe čteš shora dolů jako krok za krokem.
   - Query DSL zůstává potřeba pro věci, co ES|QL (zatím) neumí: plnotextové
     vyhledávání s relevance scoringem, geo-dotazy, percolator a hodně
     specifické vnořené agregace.
