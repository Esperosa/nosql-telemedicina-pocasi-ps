-- Dotaz 1: Fyzická distribuce dat na shardy přes $shardedDataDistribution (POVINNÝ DOTAZ)
--------------------------------------------------------------------------------
1. Zadání v přirozeném jazyce:
Zobrazte fyzické rozložení datové sady a chunků kolekce 'sensor_readings' napříč všemi
shardy clusteru (shard1rs, shard2rs, shard3rs) za účelem vyhodnocení rovnoměrnosti

2. Přesný příkaz (mongosh):

4. Vysvětlení chování příkazu:
Agregační stupeň $shardedDataDistribution je nativní operátor zavedený v moderních verzích
MongoDB. Dotazuje přímo konfigurační servery (cfgrs) a dotčené shardy, odkud agreguje exaktní
počty dokumentů a zabranou velikost v bajtech pro každou replikační sadu shardu bez nutnosti
spouštět náročné manuální scanování celé kolekce. Musí se spouštět na databázi "admin",
protože jde o cluster-wide dotaz nad metadaty ze všech shardů, ne o operaci nad jednou
konkrétní databází.

shard1rs drží 2 629 dokumentů (32,9 %), shard2rs 2 970 dokumentů (37,1 %) a shard3rs

funkce rozděluje klíče rovnoměrně jen statisticky, ne do identických bloků, a u 500 unikátních
pacientů (kardinalita shard key) se s tak malým počtem hodnot projeví přirozený rozptyl.
Důležité je, že žádný shard nemá výrazně víc dat než ostatní (žádný "hotspot").

stejný poslední shard, ale rozptylují se mezi všechny tři - přesně to, proč byl zvolen
hashovaný shard key místo přímého patient_id.

-- Dotaz 3: Simulace výpadku primárního uzlu shardu (Cluster Failover — PŘED / BĚHEM / PO)
--------------------------------------------------------------------------------
1. Zadání v přirozeném jazyce:
Proveďte simulaci havárie primárního uzlu první replikační sady (shard1a). Dokažte stav
replikace před výpadkem, úspěšnou volbu nového PRIMARY uzlu během výpadku, schopnost
clusteru obsloužit zápis s writeConcern "majority" a následnou resynchronizaci po obnově uzlu.

2. Přesný příkaz (mongosh):
// Krok A: Zjištění aktuálního PRIMARY uzlu na shard1rs

// Krok F: [Obnova uzlu v terminálu: docker start shard1a]

4. Vysvětlení chování příkazu:
MongoDB replica set používá konsenzuální protokol odvozený z Raftu. Pokud PRIMARY uzel
přestane odpovídat na heartbeaty (timeout 10 s), zbývající uzly (shard1b a shard1c) vyhlásí volby.
Jelikož mají 2 hlasy ze 3 (přísná většina > 50 %), shard1b je zvolen novým PRIMARY.
Zápis s writeConcern w: "majority" uspěje, protože se potvrdí na shard1b a shard1c.
Po restartu se shard1a připojí jako SECONDARY, dočte chybějící operace z oplogu a je synchronní.

5. Interpretace výsledku:
Cluster disponuje plnou tolerancí vůči výpadku 1 uzlu v každém shardu. Klientská aplikace
napojená na mongos router nezaznamená výpadek ani ztrátu dat — router automaticky přesměruje
zápisy na nově zvolený uzel shard1b.

zastaralých dat při současném odlehčení primárního uzlu.

2. Přesný příkaz (mongosh):
// Zjištění stavu a zpoždění replikace na shard1rs:
rs.printSecondaryReplicationInfo();

const session = db.getMongo().startSession({ causalConsistency: true });
const secColl = session.getDatabase("telemedicina").getCollection("sensor_readings");

secColl.find(
  { "vitals.heart_rate": { $gt: 140 } },
  { reading_id: 1, patient_id: 1, "vitals.heart_rate": 1, alert_type: 1 }

      phone: "$patient_info.contact.phone",

      risk_category: "$patient_info.risk_category"

-- Dotaz 6: Vícedimenzionální analytický přehled monitoringu ($facet)
--------------------------------------------------------------------------------
1. Zadání v přirozeném jazyce:
Během jednoho průchodu daty vygenerujte souhrnný manažerský přehled obsahující:
(a) rozložení poplachů podle typu senzoru, (b) statistiku senzorů s kriticky nízkou baterií (< 20 %),
(c) celkové globální průměry fyziologických funkcí.

2. Přesný příkaz (mongosh):
use telemedicina;
db.sensor_readings.aggregate([
  { $facet: {
      "poplachy_dle_senzoru": [
        { $match: { alert_triggered: true } },
        { $group: { _id: "$device_type", pocet_poplachu: { $sum: 1 } } },
        { $sort: { pocet_poplachu: -1 } }
      ],
      "vybite_senzory": [
        { $match: { battery_level: { $lt: 20 } } },
        { $group: {
            _id: "$device_type",
            pocet_zarizeni: { $sum: 1 },
            prumerna_baterie: { $round: [{ $avg: "$battery_level" }, 1] }
        } }
      ],
      "globalni_prumery": [
        { $group: {
            _id: null,
            prumerny_tep: { $round: [{ $avg: "$vitals.heart_rate" }, 1] },
            prumerny_tlak_sys: { $round: [{ $avg: "$vitals.systolic_bp" }, 1] },
            prumerny_tlak_dia: { $round: [{ $avg: "$vitals.diastolic_bp" }, 1] },
            prumerna_saturace_spo2: { $round: [{ $avg: "$vitals.spo2" }, 2] },
            celkem_odectu: { $sum: 1 }
        } }
      ]
  } }
]);

výskyty a $addToSet nasbírá unikátní patient_id, $size pak spočítá jejich počet.

5. Interpretace výsledku:
EKG náplasti a náramkové monitory zachycují nejvíc kritických hodnot, protože měří kontinuálně
(často), zatímco glukometr jen občas — to je očekávaný, snadno vysvětlitelný výsledek. Žádná
statistika se tu nepočítá, jen tři pevné klinické hranice, takže se dá u obhajoby popsat v
jedné větě: "vyberu záznamy mimo bezpečný rozsah a spočítám je po typech zařízení."

-- Dotaz 15: Distribuovaná ACID transakce napříč shardy (Eskalace péče)
--------------------------------------------------------------------------------
1. Zadání v přirozeném jazyce:
Proveďte atomickou multi-dokumentovou transakci napříč shardy: při záchytu kritického
odečtu (READ-0009999) současně v jedné transakci zapište odečet do 'sensor_readings',
změňte rizikovou kategorii pacienta v 'patients' na CRITICAL a vygenerujte urgentní žádanku
v 'medical_interventions' s plnou zárukou atomicity a konzistence snapshot.

2. Přesný příkaz (mongosh):
use telemedicina;
const session = db.getMongo().startSession();
session.startTransaction({
  readConcern: { level: "snapshot" },
  writeConcern: { w: "majority" }
});

try {
  const readingsColl = session.getDatabase("telemedicina").getCollection("sensor_readings");
  const patientsColl = session.getDatabase("telemedicina").getCollection("patients");
  const intervColl = session.getDatabase("telemedicina").getCollection("medical_interventions");

  // 1. Zápis extrémní telemetrie
  readingsColl.insertOne({
    reading_id: "READ-0009999",
    patient_id: "PAT-0002",
    device_id: "DEV-ECG-1002",
    device_type: "ECG_PATCH",
    timestamp: new Date().toISOString(),
    vitals: {
      heart_rate: 195,
      systolic_bp: 225,
      diastolic_bp: 135,
      spo2: 89.0,
      blood_glucose: 6.8,
      body_temp: 37.2
    },
    battery_level: 92,
    firmware_version: "v3.0.1",
    alert_triggered: true,
    alert_type: "HYPERTENSIVE_CRISIS"
  });

  // 2. Eskalace rizikové kategorie v evidenci pacientů
  patientsColl.updateOne(
    { patient_id: "PAT-0002" },
    { $set: { risk_category: "CRITICAL" } }
  );

  // 3. Automatické vystavení akutní žádanky o zásah
  intervColl.insertOne({
    intervention_id: "INT-00999",
    patient_id: "PAT-0002",
    doctor_id: "DOC-102",
    timestamp: new Date().toISOString(),
    trigger_type: "VITAL_ALERT",
    severity: "CRITICAL",
    notes: "Akutní eskalace péče: záchyt hypertenzní krize 225/135 a tachykardie 195 bpm.",
    medication_change: {
      prescribed_drug: "Urapidil",
      dosage_mg: 25.0,
      frequency: "i.v. statim"
    },
    hospitalization_required: true,
    follow_up_days: 1
  });

  session.commitTransaction();
  print(">>> DISTRIBUOVANÁ TRANSAKCE ÚSPĚŠNĚ POTVRZENA (COMMIT).");
} catch (error) {
  session.abortTransaction();
  print(">>> TRANSAKCE SELHALA A BYLA VRÁCENA (ABORT): " + error.message);
} finally {
  session.endSession();
}

// Ověření atomické konzistence po potvrzení transakce
const patCheck = db.patients.findOne({ patient_id: "PAT-0002" }, { patient_id: 1, risk_category: 1 });
const intervCheck = db.medical_interventions.findOne({ intervention_id: "INT-00999" });
printjson({ pacient: patCheck, intervence: intervCheck ? intervCheck.intervention_id : null });

3. Očekávaný výstup z konzole:
>>> DISTRIBUOVANÁ TRANSAKCE ÚSPĚŠNĚ POTVRZENA (COMMIT).
{
  pacient: {
    _id: ObjectId('...'),
    patient_id: 'PAT-0002',
    risk_category: 'CRITICAL'
  },
  intervence: 'INT-00999'
}

4. Vysvětlení chování příkazu:
Jde o to samé jako bankovní převod mezi účty: buď projdou úplně všechny tři zápisy (odečet +
změna rizikové kategorie + žádanka), nebo neprojde ani jeden — nic mezi tím. MongoDB tohle hlídá
sama přes `session.startTransaction()` / `commitTransaction()` / `abortTransaction()`. Protože
zápisy míří do tří různých kolekcí (a tedy potenciálně na různé shardy), mongos interně koordinuje
potvrzení mezi uzly (tzv. two-phase commit) — ale z pohledu toho, co píšu do kódu, se to chová
úplně stejně jako transakce v obyčejné jednoserverové databázi, jen o kus pod kapotou.

5. Interpretace výsledku:
Nemůže nastat půl-hotová situace — třeba že se zapíše kritický odečet, ale pacient zůstane
omylem v nekritické kategorii, protože druhý zápis selhal. Buď se stane celý "balíček" tří
zápisů najednou, nebo se celý vrátí zpátky (`abortTransaction`) a nic se nezmění.
